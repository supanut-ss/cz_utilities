# Baton — สเปกระบบสั่งงานทีม AI หลายตัว

Oct 22, 2026 · @Supanut

## ภาพรวม

Baton ให้คนคนเดียวสั่งงานทีม AI จากหลายผู้ให้บริการได้ในเว็บแอปเดียว AI แต่ละตัวแบ่งงานกัน ส่งต่องานให้กัน และหยุดรอให้คนอนุมัติเมื่อจำเป็น

- **ปัญหา:** ถ้าจะใช้ AI หลายตัวตอนนี้ ต้องคัดลอกข้อความไปมาระหว่างหน้าแชท ไม่มีบริบทร่วม ไม่มีการส่งต่องาน และคุมค่าใช้จ่ายไม่ได้
- **กลุ่มผู้ใช้:** คนทำงานและทีมเล็กในไทย (รายงาน คอนเทนต์ ค้นคว้า รีวิวโค้ด) ที่ไม่ได้เชี่ยวชาญการเขียน prompt
- **เป้าหมาย MVP:** ผู้ใช้พิมพ์เป้าหมายเป็นภาษาไทย รับทีมที่ระบบแนะนำ แล้วได้ผลงานที่ผ่านการตรวจ พร้อมจุดอนุมัติ ทุกงานแสดงความคืบหน้า token และค่าใช้จ่ายแบบสด
- **ยังไม่ทำใน MVP:** ตัวแก้ไขแบบลากต่อกล่อง (node graph) การใช้งานร่วมกันหลายคน ตลาดทักษะ และแอปมือถือ

หลักการออกแบบ:

1. **เสนอให้ก่อน ค่อยปรับทีหลัง** ระบบจัดทีมและลำดับงานให้ การแก้ไขเป็นทางเลือก
2. **มีคนอยู่ในวงจรเสมอ** AI ถามเมื่อไม่แน่ใจ และทุกอย่างที่ส่งออกนอกแอปต้องได้รับอนุมัติ
3. **ส่งต่อด้วยเอกสาร ไม่ใช่ประวัติแชท** การส่งต่องานทุกครั้งเป็นใบงานที่มีโครงสร้าง
4. **เห็นค่าใช้จ่ายตลอด** token และเงินบาท แยกตาม AI แต่ละตัว รายงาน และรายเดือน

"Baton" (ไม้ผลัดวิ่งส่งต่อ) เป็นชื่อชั่วคราว หน้าจอใช้ภาษาไทย มีฉบับภาษาอังกฤษอยู่ที่ [Baton — Multi-AI Team Orchestrator Spec](https://claude.ai/artifact/ReFQhtDiLtAgDdhBUZfwXQ)

| 2 | ทีมกำลังทำงาน | ดูและคุมงานที่รันอยู่ | แถบขั้นตอน, การ์ด AI พร้อมสถานะ ความคืบหน้า และ token, ไทม์ไลน์การส่งต่อ, คำถามจาก AI พร้อมปุ่มตอบ, ช่องสั่งงานด้วย @ชื่อ, ตัวอย่างผลงานล่าสุด |

| 4 | ลำดับงาน | กำหนดการส่งต่อ | 3 รูปแบบการทำงาน, รายการขั้นตอนที่ลากสลับได้, เส้นทางเมื่อผ่าน/ไม่ผ่าน, จำนวนรอบแก้สูงสุด, ขั้นอนุมัติ, กติกาทีม (งบ เวลา ตัวสำรอง ความจำร่วม) |
| 5 | คลังทักษะ | จัดการทักษะที่ใช้ซ้ำได้ | รายการทักษะ, ส่วนแก้ไข (ใช้เมื่อไหร่ คู่มือ ไฟล์ เครื่องมือที่ต้องใช้), token ที่ใช้ในแต่ละระดับการโหลด, เวอร์ชัน, นำเข้า SKILL.md |
| 6 | เบื้องหลังระบบ | ไดอะแกรมแนวคิด | ผู้ใช้ → ตัวคุมงาน → AI แต่ละตัว → ผู้ให้บริการ พร้อมความจำร่วม |
| 7 | สถาปัตยกรรมระบบ | ไดอะแกรมระบบ | เว็บ, API, Redis, worker, ที่เก็บข้อมูล, ผู้ให้บริการ AI |

ลำดับการใช้งานหลัก:

1. ผู้ใช้พิมพ์เป้าหมายที่หน้า 1 แล้วกด "จัดทีมให้"
2. นักวางแผนเสนอ AI รุ่น และขั้นตอน ผู้ใช้กดรับ หรือปรับที่หน้า 3 และ 4
3. กด "เริ่มทำงาน" แล้วหน้า 2 แสดงความคืบหน้าแบบสด
4. AI ส่งต่องานกัน ตัวไหนไม่แน่ใจจะตั้งคำถามพร้อมตัวเลือกให้ตอบ
5. ผู้ตรวจงานให้ผ่าน หรือส่งกลับให้แก้ได้ไม่เกินจำนวนรอบที่ตั้งไว้
6. ผู้ใช้อนุมัติผลงานสุดท้าย แล้วระบบบันทึกไว้กับงานนั้น

ภาพลักษณ์: ฟอนต์ IBM Plex Sans Thai คู่กับ IBM Plex Mono สำหรับตัวเลข พื้นหลังโทนเทาเย็น สีเน้นสีน้ำเงินสีเดียว (#2D5BFF) AI แต่ละตัวมีตัวอักษรประจำตัวคู่กับชื่อ และปุ่มกดต้องใหญ่อย่างน้อย 44 px

## สถาปัตยกรรม

ทุกขั้นของ AI เป็น job ในคิวที่บันทึกสถานะลง Postgres งานจึงรออนุมัติได้หลายชั่วโมง และทำต่อได้หลัง worker ล่ม

&#91;embedded content: สถาปัตยกรรมระบบ · 10 ส่วนประกอบ\]

ไม่มี worker ไหนถืองานไว้ในหน่วยความจำระหว่างขั้น ผลลัพธ์ไปอยู่ใน Postgres ส่วนอีเวนต์ไปถึงเบราว์เซอร์ผ่าน Redis และ SSE

งานหนึ่งเดินผ่านระบบทีละขั้น:

1. API บันทึกงานพร้อมล็อกเวอร์ชัน flow แล้วใส่ขั้นแรกลงคิว
2. worker ดึงขั้นนั้นมา จัดบริบท เรียกโมเดลผ่าน gateway และรัน tool call ที่โมเดลขอ
3. ผลงานถูกบันทึกเป็น artifact พร้อมใบงานสำหรับขั้นถัดไป แล้วส่งอีเวนต์ไป Redis
4. API ส่งอีเวนต์เหล่านั้นต่อไปที่เบราว์เซอร์ผ่าน SSE
5. ถ้ามีคำถามหรือต้องอนุมัติ งานเปลี่ยนเป็นสถานะรอแล้ว job จบลง เมื่อผู้ใช้ตอบจึงใส่ขั้นถัดไปลงคิว

## Tech stack

ใช้ TypeScript ทั้งระบบใน monorepo เดียว หน้าจอกับ engine จึงใช้ schema ชุดเดียวกัน

| ชั้น | สิ่งที่เลือก | เหตุผล |
| --- | --- | --- |
| โครงโปรเจกต์ | pnpm + Turborepo: `apps/web`, `apps/worker`, `packages/core`, `packages/llm-gateway`, `packages/tools` | แชร์ Zod schema ของใบงาน flow และอีเวนต์ |
| หน้าจอ + API | Next.js (UI, REST route handlers, SSE), Tailwind + shadcn/ui, dnd-kit, TanStack Query | ตรงกับดีไซน์ และ deploy UI กับ API เป็นก้อนเดียว |
| อัปเดตสด | Server-Sent Events ส่วนคำสั่งส่งทาง REST | ข้อมูลไหลทางเดียวพอ และต่อใหม่จากอีเวนต์ล่าสุดได้ |
| คิว + อีเวนต์ | Redis + BullMQ และ Redis pub/sub | มี retry, งานหน่วงเวลา (เตือนซ้ำ), จำกัดอัตราเรียกต่อเจ้า |
| ฐานข้อมูล | PostgreSQL + Drizzle ORM (เพิ่ม pgvector ทีหลัง) | เก็บงาน ขั้นตอน อีเวนต์ ค่าใช้จ่าย และทักษะไว้ที่เดียว |
| ไฟล์ | S3-compatible (Cloudflare R2; ตอนพัฒนาใช้ MinIO) | ไฟล์แนบ ผลงาน และไฟล์ประกอบทักษะ |
| การเรียก AI | `LLMGateway` interface ของเราเอง ครอบ SDK ทางการของแต่ละเจ้า | ฟีเจอร์ใหม่มักมาใน SDK ทางการก่อน |
| เครื่องมือ | Tool registry แบบ MCP, Tavily สำหรับค้นเว็บ, E2B สำหรับ sandbox รันโค้ด | AI ทุกเจ้าได้เครื่องมือชุดเดียวกัน |
| ล็อกอิน | Auth.js กับ LINE Login และ Google | คนไทยใช้ LINE เป็นหลัก |
| แจ้งเตือน | LINE Messaging API, อีเมลผ่าน Resend | LINE Notify ปิดบริการไปแล้วเมื่อมี.ค. 2025 |
| ติดตามระบบ | Langfuse, OpenTelemetry, Sentry | ดู prompt token และ error ได้ทีละขั้น |
| Deploy | Docker: web, worker หลายตัว; Postgres และ Redis แบบ managed; region สิงคโปร์ | SSE ที่เปิดนานและงานที่รันนานไม่เหมาะกับ serverless |

## Flow engine และการส่งต่องาน

Flow engine เป็น state machine ที่เก็บสถานะไว้ในฐานข้อมูล หนึ่งขั้นคือหนึ่ง job การรอคนตอบจึงไม่กินทรัพยากรเครื่อง

&#91;embedded content: สถานะของงาน · 6 สถานะ\]

มีแค่สถานะ "กำลังทำงาน" ที่ใช้ worker และใช้ทีละขั้น สถานะอื่นเป็นแค่แถวข้อมูลใน Postgres

| รูปแบบ | engine ทำงานยังไง |
| --- | --- |
| ส่งต่อเป็นทอด | ทำทีละขั้น ขั้นถัดไปได้รับใบงานจากขั้นก่อนหน้า |
| แบ่งงานทำพร้อมกัน | ขั้นที่มี AI หลายตัวใส่ job ลงคิวตัวละหนึ่งงาน แล้วรอให้ครบ (หรือตัวแรกเสร็จ) ก่อนรวมผล |
| มีหัวหน้าสั่งงาน | AI หัวหน้าได้เครื่องมือ `delegate(agent, task)` และ `finish(result)` งานที่แตกออกไปรันเป็นขั้นย่อย ลึกได้ชั้นเดียว |

กติกา:

- **วนแก้งาน:** ผู้ตรวจงานส่งผลตัดสินกลับมา ถ้าไม่ผ่าน engine สร้างขั้นใหม่ให้ AI ที่ถูกระบุพร้อมปัญหา และนับรอบเพิ่ม ครบจำนวนรอบสูงสุดแล้วถามผู้ใช้
- **AI ค้าง:** ทุกขั้นมี timeout เกินแล้วถามผู้ใช้
- **คำถาม:** AI ทุกตัวมีเครื่องมือ `ask_user(question, options)` เมื่อเรียก ขั้นนั้นหยุด และงานเปลี่ยนเป็นสถานะ "รอคุณ"
- **เตือนซ้ำ:** BullMQ job แบบหน่วงเวลาส่งเตือนผ่าน LINE ตามที่ flow กำหนด

ใบงานที่ส่งต่อกันระหว่าง AI (ตรวจด้วย Zod schema ชุดเดียวกัน และให้โมเดลสร้างผ่าน structured outputs):

```json
{
  "run_id": "run_123",
  "from": "planner",
  "to": "writer",
  "task": "ร่างโครงรายงานและบทนำ",
  "inputs": [{ "artifact_id": "art_9", "summary": "ตารางยอดขายแยกแบรนด์ ชุดที่ 1" }],
  "expected_output": { "type": "document", "schema": "report_draft_v1" },
  "acceptance": ["ทุกตัวเลขต้องมีแหล่งที่มา", "ยาวไม่เกิน 2 หน้า"],
  "budget_tokens": 20000
}
```

ผลตัดสินจากผู้ตรวจงาน:

```json
{
  "verdict": "fail",
  "issues": [{ "where": "ส่วนที่ 2", "problem": "ยอดขายปี 2025 ไม่มีแหล่งที่มา", "fix_by": "researcher" }]
}
```

## LLM gateway และรุ่นโมเดล

มี `LLMGateway` interface เดียว และมี adapter แยกต่อผู้ให้บริการ แต่ละตัวสร้างบน SDK ทางการของเจ้านั้น (`@anthropic-ai/sdk`, OpenAI, Google GenAI, Ollama)

- **Interface:** `generate()` (แบบ streaming), `countTokens()`, `listModels()` คำขอใช้รูปแบบกลาง: system, messages, tools, output schema, max tokens, คำแนะนำเรื่อง effort
- **คำตอบรูปแบบกลาง:** เนื้อหา, tool calls, stop reason และ usage ที่แยก input, output, cache read, cache write
- **รายชื่อรุ่น:** ดึงจาก Models API ของแต่ละเจ้าตอนเริ่มระบบ ไม่ hardcode และได้ขนาด context window จากที่เดียวกัน

ระดับรุ่น (สิ่งที่ผู้ใช้เลือกที่หน้าตั้งค่าทีม):

| ระดับ | Anthropic | เจ้าอื่น |
| --- | --- | --- |
| เก่งที่สุด | `claude-opus-5-5` | ตั้งใน config ตารางระดับรุ่น |
| สมดุล | `claude-sonnet-5-5` | ตั้งใน config ตารางระดับรุ่น |
| เร็วและประหยัด | `claude-haiku-5-5` | ตั้งใน config; โมเดลในเครื่องผ่าน Ollama |

ข้อควรรู้ฝั่ง Claude:

- ใช้ structured outputs (`output_config.format`) เพื่อให้ได้ใบงานเป็น JSON เพราะ Opus 5.5 และ Sonnet 5.5 ตอบ error 400 เมื่อบังคับ `tool_choice`
- ตั้ง `effort` ให้ AI แต่ละตัวเอง เพราะค่าเริ่มต้นของ Opus 5.5 คือ `medium` การคิดเป็นแบบ adaptive และปิดไม่ได้บน Opus 5.5
- เช็ก `stop_reason: "refusal"` ทุกคำตอบ แล้วส่งต่อไปทางตัวสำรอง
- ใช้ streaming กับคำตอบยาว และวางส่วนที่คงที่ไว้ต้น prompt เพื่อให้ prompt caching ทำงาน
- thinking block ผูกกับรุ่นที่สร้าง ห้ามส่งประวัติดิบของ AI ตัวหนึ่งไปให้โมเดลอื่น ให้ส่งใบงานแทน

ลำดับตัวสำรอง: SDK retry เมื่อเจอ 429/5xx ต่อด้วยรุ่นระดับเดียวกันของเจ้าอื่น แล้วค่อยหยุดถามผู้ใช้ การสลับรุ่นทำให้ prompt cache ของ AI ตัวนั้นหาย และบันทึกไว้ในบัญชีค่าใช้จ่าย

Claude Agent SDK และ Managed Agents ใช้ได้กับ Claude อย่างเดียว จึงไม่ใช้เป็นแกน แต่นำมาทำ AI เขียนโค้ดที่ใช้ Claude อย่างเดียวได้ภายหลัง

## การจัดการ token

นับ token ก่อนเรียกทุกครั้ง และคุมงบ 3 ชั้น: ต่องาน ต่อขั้น และต่อคำตอบ

| ชั้น | ตั้งที่ไหน | เมื่อถึงเพดาน |
| --- | --- | --- |
| ต่องาน | งบเป็นบาท (หน้าลำดับงาน กติกาทีม) | หยุดงานแล้วถามผู้ใช้ว่าจะเพิ่มงบหรือหยุด |
| ต่อขั้น | งบ token ต่อขั้นของ AI แต่ละตัว (หน้าตั้งค่าทีม) | ตัวจัดบริบทตัดหรือสรุปข้อมูลก่อนเรียก |
| ต่อคำตอบ | ความยาวคำตอบสูงสุด (หน้าตั้งค่าทีม) | คำตอบถูกจำกัดความยาว งานที่เหลือทำต่อในรอบถัดไป |

กลไกที่ใช้:

- **นับก่อนเรียก:** adapter ใช้ตัวนับของแต่ละเจ้า (ฝั่ง Claude ใช้ `count_tokens`) แล้ว engine ประมาณค่าใช้จ่ายจากตารางราคาก่อนเรียกทุกครั้ง
- **บริบทไม่บวม:** ตัวจัดบริบทส่งเฉพาะไฟล์ที่ใบงานอ้างถึง ของเก่าให้ `claude-haiku-5-5` สรุปก่อน และตัดเนื้อหาเว็บที่ดึงมาให้สั้นลง
- **วนใช้เครื่องมือนานๆ:** AI ฝั่ง Claude ใช้ compaction หรือ context editing ส่วนเจ้าอื่นใช้ตัวสรุปของเราเอง task budget ของ Claude (ยังเป็น beta) ช่วยให้โมเดลรู้งบและคุมจังหวะเอง
- **Effort:** AI ที่งานง่ายใช้ effort ต่ำ ส่วนนักวางแผนและผู้ตรวจงานใช้สูงกว่า
- **Prompt cache:** เรียงทุก prompt เป็น tools → role prompt และรายชื่อทักษะ (เรียงตายตัว) → งาน cache แยกตามรุ่น จึงควรให้ AI แต่ละตัวใช้รุ่นเดิมให้นานที่สุด
- **บัญชีค่าใช้จ่าย:** เก็บ input, output, cache read, cache write แยกกันทุกครั้งที่เรียก เพราะราคาไม่เท่ากัน หน้า 2 และ 3 อ่านข้อมูลจากตรงนี้
- **ภาษาไทย:** เนื้อหาเดียวกัน ภาษาไทยมักใช้ token มากกว่าอังกฤษ ให้ทดสอบเขียน prompt และใบงานภายในเป็นอังกฤษ แต่ผลงานสุดท้ายเป็นไทย แล้วเลือกแบบที่ถูกกว่าเมื่อคุณภาพเท่ากัน

## ระบบทักษะ (Skills)

ทักษะคือคู่มือการทำงานที่ AI โหลดมาใช้เมื่อต้องใช้เท่านั้น ติด 20 ทักษะจึงกินแค่ราว 1k token ตอนที่ยังไม่ได้ใช้

- **รูปแบบ:** โฟลเดอร์ที่มี `SKILL.md` (frontmatter: ชื่อ, คำอธิบาย, เวอร์ชัน, เครื่องมือที่ต้องใช้; เนื้อหา: คู่มือ) พร้อม `files/` และ `scripts/` ถ้ามี เป็นรูปแบบเดียวกับ Agent Skills จึงนำเข้าทักษะที่มีอยู่แล้วได้
- **เก็บที่ไหน:** ข้อมูลทักษะและเวอร์ชันอยู่ใน Postgres ไฟล์อยู่ใน object storage จัดการผ่านหน้าคลังทักษะ

การโหลดทีละชั้น:

1. **อยู่ในบริบทตลอด:** ชื่อกับคำอธิบายว่า "ใช้เมื่อไหร่" ของทุกทักษะที่ติดไว้ ประมาณ 50 token ต่อทักษะ อยู่ในส่วนที่คงที่ต้น prompt
2. **โหลดเมื่อต้องใช้:** AI เรียก `load_skill(name)` แล้วได้คู่มือเต็มกลับมาเป็น tool result (ราว 1–2k token)
3. **เปิดเฉพาะที่จำเป็น:** `read_skill_file(name, path)` เปิดทีละไฟล์ ส่วน `run_skill_script` รันสคริปต์ใน sandbox เท่านั้น ไม่รันใน worker

กติกา:

- **ไม่เพิ่มสิทธิ์:** การติดทักษะไม่ได้ให้สิทธิ์เครื่องมือ engine ยังเช็กสิทธิ์ของ AI ตัวนั้น และหน้าจอเตือนถ้าขาดเครื่องมือที่ต้องใช้
- **ล็อกเวอร์ชัน:** งานที่กำลังรันล็อกเวอร์ชันทักษะที่ใช้ตอนเริ่ม เหมือน flow แก้ไขทักษะจะกลายเป็นเวอร์ชันใหม่
- **ทดสอบก่อน:** ปุ่ม "ทดสอบกับ AI" รันทักษะกับเป้าหมายตัวอย่างที่บันทึกไว้ ก่อนเผยแพร่เวอร์ชันใหม่
- **ทักษะที่นำเข้าถือว่าไม่น่าเชื่อถือ:** ปิดไว้จนกว่าจะตรวจ และสคริปต์รันได้เฉพาะใน sandbox
- **อีเวนต์:** การโหลดทุกครั้งบันทึกเป็นอีเวนต์ `skill_loaded` พร้อมจำนวน token และแสดงในไทม์ไลน์หน้าทีมกำลังทำงาน

ในอนาคต AI ฝั่ง Claude ใช้ Skills API ของ Anthropic เองได้ ซึ่งต้องใช้ code execution บน container ของ Anthropic ส่วน MVP ใช้ตัวโหลดของเราเอง เพื่อให้ทุกเจ้าทำงานเหมือนกัน

## ความปลอดภัยและความเป็นส่วนตัว

กติกาความปลอดภัยบังคับด้วยโค้ดใน engine ไม่ฝากไว้กับ prompt

- **API key:** เข้ารหัสด้วย envelope encryption (AES-256-GCM, master key อยู่ใน KMS) ถอดรหัสเฉพาะในหน่วยความจำของ worker และไม่ส่งไปที่เบราว์เซอร์
- **สิทธิ์เครื่องมือ:** AI แต่ละตัวมีรายการเครื่องมือที่อนุญาตจากหน้าตั้งค่าทีม Tool Runtime ปฏิเสธทุกการเรียกที่อยู่นอกรายการ
- **ด่านอนุมัติ:** อีเมล โพสต์ ไฟล์ที่แชร์ และทุกอย่างที่ออกนอกแอป ต้องรอผู้ใช้อนุมัติเสมอ ไม่ว่าโมเดลจะตอบอะไร
- **เนื้อหาที่ไม่น่าเชื่อถือ:** หน้าเว็บ ไฟล์ที่อัปโหลด และทักษะที่นำเข้า ถูกครอบและติดป้ายว่าเป็นข้อมูล คำสั่งที่ฝังอยู่ข้างในจะไม่ถูกทำตาม
- **การรันโค้ด:** รันใน E2B sandbox เท่านั้น ไม่มี secret และจำกัดการเชื่อมต่อออกอินเทอร์เน็ต
- **แยกข้อมูลแต่ละ workspace:** ทุกแถวมี `workspace_id` และใช้ row-level security ของ Postgres เป็นชั้นที่สอง
- **Audit:** `run_events` เป็นแบบเพิ่มอย่างเดียว บันทึกว่าใครหรืออะไรทำแต่ละอย่าง
- **PDPA:** แสดงว่าข้อมูลของ AI แต่ละตัวส่งไปผู้ให้บริการไหน ให้เลือกโมเดลในเครื่องสำหรับงานที่มีข้อมูลอ่อนไหว ตั้งระยะเก็บข้อมูลต่อ workspace และลบข้อมูลงานเมื่อมีคำขอ

## โมเดลข้อมูล

มีตารางหลัก 18 ตารางใน PostgreSQL ทุกตารางยกเว้น `workspaces` และ `users` มี `workspace_id`

| ตาราง | เก็บอะไร |
| --- | --- |
| `users`, `workspaces` | บัญชีผู้ใช้ ตัวตน LINE/Google และค่าตั้ง workspace (ระยะเก็บข้อมูล งบรายเดือน) |
| `provider_keys` | API key ที่เข้ารหัสแล้วต่อผู้ให้บริการ และค่าจำกัดอัตราเรียก |
| `agents` | ชื่อ, role prompt, ผู้ให้บริการ, ระดับ/รุ่น, effort, เครื่องมือที่อนุญาต, งบ token ต่อขั้น, ความยาวคำตอบสูงสุด |
| `teams` | ชุดของ AI ที่ตั้งชื่อไว้ |
| `flows`, `flow_versions` | รูปแบบ, ขั้นตอน (AI, เงื่อนไขส่งต่อ, วิธีรวมผล, เส้นทางผ่าน/ไม่ผ่าน, รอบแก้สูงสุด), กติกาทีม |
| `runs` | เป้าหมาย, เวอร์ชัน flow ที่ล็อกไว้, สถานะ, งบ, ยอดรวม (token, บาท), เวลาเริ่ม/จบ |
| `steps` | งาน, ขั้น, AI, รอบ, สถานะ, รุ่นที่ใช้จริง, อ้างอิงไฟล์เข้า/ออก, usage |
| `handoffs` | ใบงานระหว่าง AI: จาก, ถึง, งาน, ข้อมูลนำเข้า, ผลที่คาดหวัง, เกณฑ์รับงาน |
| `questions` | คำถามและคำขออนุมัติจาก AI: ตัวเลือก, คำตอบ, ผู้ตอบ, กำหนดการเตือน |
| `artifacts` | ไฟล์และผลงานพร้อมเวอร์ชัน เนื้อหาอยู่ใน object storage |
| `run_events` | บันทึกอีเวนต์แบบเพิ่มอย่างเดียว (seq, type, payload) ใช้ทำไทม์ไลน์ เล่นซ้ำผ่าน SSE และ audit |
| `cost_ledger` | หนึ่งแถวต่อการเรียก AI: token input, output, cache read, cache write, ราคา, บาท |
| `skills`, `skill_versions`, `skill_files` | ข้อมูลทักษะ, คู่มือแต่ละเวอร์ชัน, ไฟล์ประกอบ |
| `agent_skills` | AI แต่ละตัวติดทักษะเวอร์ชันไหนไว้ |

ขอบเขต MVP:

## คำถามที่ยังเปิดอยู่และความเสี่ยง

มี 4 เรื่องที่ต้องตัดสินใจก่อนเริ่มพัฒนา:

- [ ] **รูปแบบการเก็บเงิน:** ผู้ใช้ใส่ API key เอง หรือแพลตฟอร์มขายเครดิตแบบเติมเงินก่อน เรื่องนี้กระทบการเก็บ key บัญชีค่าใช้จ่าย และระบบชำระเงิน
- [ ] **Region ที่ตั้งระบบ:** ใช้ cloud region สิงคโปร์ หรือผู้ให้บริการในไทยเพื่อให้ข้อมูลอยู่ในประเทศ
- [ ] **รุ่นของเจ้าอื่น:** รุ่นไหนของ OpenAI และ Google จะอยู่ในระดับ เก่งที่สุด / สมดุล / เร็วและประหยัด ตอนเปิดตัว
- [ ] **ภาษาของ prompt ภายใน:** อังกฤษหรือไทย สำหรับ prompt และใบงาน ตัดสินจากการทดสอบ token และคุณภาพ

| ความเสี่ยง | ผลกระทบ | วิธีรับมือ |
| --- | --- | --- |
| ค่าใช้จ่ายบานปลายจากการวนแก้หรือโหมดหัวหน้า | บิลสูงกว่าที่ประมาณไว้มาก | หยุดทันทีเมื่องบงานหมด, จำกัดรอบแก้, หัวหน้าแตกงานได้ชั้นเดียว |
| API ของผู้ให้บริการเปลี่ยน (เช่น Claude 5.5 ไม่รับการบังคับเรียก tool) | ขั้นตอนพังหลังอัปเกรด | contract test ต่อ adapter, ล็อกเวอร์ชัน SDK, เช็ก Models API ตอนเริ่มระบบ |
| Prompt injection จากหน้าเว็บ ไฟล์ หรือทักษะที่นำเข้า | ข้อมูลรั่วหรือทำสิ่งที่ไม่ควรทำ | ด่านอนุมัติก่อนส่งออก, ติดป้ายเนื้อหาไม่น่าเชื่อถือ, รันสคริปต์ใน sandbox |
| คุณภาพไม่เท่ากันระหว่างผู้ให้บริการ | ผู้ใช้โทษแอป | ทดสอบด้วยเป้าหมายตัวอย่างต่อเทมเพลตก่อนเปลี่ยนรุ่นเริ่มต้น |
| คำขออนุมัติค้างไม่มีคนตอบ | งานค้างหลายวัน | เตือนผ่าน LINE, กำหนด timeout ต่อ flow, สถานะ "รอคุณ" ที่เห็นชัด |
